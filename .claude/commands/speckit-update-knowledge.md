## Pre-Execution Checks

**Check for extension hooks (before knowledge update)**:
- Check if `spec-kit/.specify/extensions.yml` exists in the project root.
- If it exists, read it and look for entries under the `hooks.before_update_knowledge` key
- If the YAML cannot be parsed or is invalid, skip hook checking silently and continue normally
- Filter out hooks where `enabled` is explicitly `false`. Treat hooks without an `enabled` field as enabled by default.
- For each remaining hook, do **not** attempt to interpret or evaluate hook `condition` expressions:
  - If the hook has no `condition` field, or it is null/empty, treat the hook as executable
  - If the hook defines a non-empty `condition`, skip the hook and leave condition evaluation to the HookExecutor implementation
- For each executable hook, output the following based on its `optional` flag:
  - **Optional hook** (`optional: true`):
    ```

    **Optional Pre-Hook**: {extension}
    Command: `/{command}`

    ```

    Executing: `/{command}`

## Execution Steps

### 1. Scan for Unintegrated Features

Scan `spec-kit/specs/` for all feature directories. For each directory:

- Check if `change-summary.md` exists (feature is delivered)
- Check if `.knowledge-integrated` marker file exists (feature is already integrated)

Build an integration queue of features where `change-summary.md` EXISTS but `.knowledge-integrated` does NOT exist.

Sort the queue by feature number (oldest first, e.g., `007` before `008` before `009`).

**If the queue is empty:**

```
## No Features to Integrate

All delivered features have already been integrated into the knowledge base.
No action required.
```

**STOP execution.**

**If features are found**, display the queue:

```
## Features Pending Knowledge Integration

| # | Feature | Directory | Delivered | Integrated |
|---|---------|-----------|-----------|------------|
| 1 | {NNN-slug} | spec-kit/specs/{NNN-slug}/ | Yes | No |
| 2 | {NNN-slug} | spec-kit/specs/{NNN-slug}/ | Yes | No |
...

Proceeding to integrate {count} feature(s), oldest first.
```

### 2. Process Each Feature (Oldest First)

For each unintegrated feature in the queue, execute steps 2a through 2g:

#### 2a. Load Feature Artifacts

Read the following from the feature directory:

- **REQUIRED**: `spec.md` — functional requirements, scope, acceptance criteria
- **REQUIRED**: `change-summary.md` — changed files, traceability matrices, commit history
- **IF EXISTS**: `plan.md` — architecture decisions, file structure, technical constraints
- **IF EXISTS**: `data-model.md` — entity/schema changes
- **IF EXISTS**: `contracts/` — API contract definitions

Extract from `change-summary.md`:
- List of all files changed (with change types: Added, Modified, Deleted)
- FR-to-file traceability mapping
- AC-to-test traceability mapping

#### 2b-pre. Incremental Scope Detection

Before identifying affected documents, check if any were recently regenerated:

1. Read `spec-kit/ai/knowledge/.generation-fingerprint.yaml` (if exists)
2. For each knowledge document that will be identified as affected in the next step:
   - Compare the document's last-modified timestamp with the fingerprint's `last_generated` timestamp
   - If the document was regenerated by speckit-generate-knowledge AFTER the feature's implementation completed: mark as `recently-regenerated`
3. For `recently-regenerated` documents:
   - Skip targeted edits (the full regeneration already incorporated the latest codebase state)
   - Still update knowledge-scores.yaml freshness to CURRENT
   - Log: `Skipping {doc} -- recently regenerated by speckit-generate-knowledge`
4. For all other affected documents: proceed with targeted edits as normal
5. After all edits are applied: update fingerprint hashes for edited documents

**Note:** If `.generation-fingerprint.yaml` does not exist, treat all documents as requiring targeted edits (no skip).

#### 2b. Identify Affected Knowledge Documents

Map the changed files to the knowledge documents they affect:

| Changed File Pattern | Affected Knowledge Doc |
|---------------------|----------------------|
| `**/controllers/**`, `**/dto/**`, `**/routes/**` | `api-spec.md` |
| `**/entities/**`, `**/repositories/**`, `**/migrations/**` | `data-model-spec.md` |
| `**/config/**`, `**/security/**`, `**/auth/**` | `security-spec.md` |
| `**/services/**`, `**/modules/**` | `architecture.md` |
| `src/app/**` (frontend), `**/*.component.*`, `**/*.module.*` | `frontend-spec.md` |
| `**/agents/**`, `**/workflow-executions/**`, `**/langchain4j/**` | `agentic-spec.md` |
| `**/rabbitmq/**`, `**/kafka/**`, `**/external/**` | `integration-spec.md` |
| `**/docker/**`, `**/k8s/**`, `**/ci/**`, `**/deploy/**` | `deployment-spec.md` |

Also consider the feature's `spec.md` scope to identify conceptual impacts not captured by file patterns alone (e.g., a new business concept that should appear in `architecture.md` even if no architecture files were directly changed).

#### 2c. Apply Targeted Edits to Knowledge Documents

For each affected knowledge document:

1. Read the current content of the knowledge doc.
2. Identify `<!-- ai-synthesized -->` sections that need updating based on the feature's changes.
3. Apply targeted edits to only the relevant `<!-- ai-synthesized -->` sections.
4. **NEVER modify `<!-- steward-authored -->` sections.**
5. Add new subsections if the feature introduces entirely new concepts not covered by existing sections.

**Edit types by knowledge doc:**

- **api-spec.md**: Add new endpoints, update existing endpoint descriptions, add new DTOs
- **data-model-spec.md**: Add new tables/columns, update relationships, document new constraints
- **architecture.md**: Update module descriptions, add new patterns, document new cross-cutting concerns
- **agentic-spec.md**: Update agent behaviors, add new workflow patterns, document new LLM integrations
- **frontend-spec.md**: Add new components/modules, update routing, document new UI patterns
- **integration-spec.md**: Add new integrations, update message broker patterns, document new external connections
- **security-spec.md**: Update security rules, add new endpoint authorization, document new security patterns
- **deployment-spec.md**: Update infrastructure requirements, add new service dependencies, update port allocations

#### 2d. Update knowledge-scores.yaml

For each affected knowledge document, update its scores:

- **freshness**: Set to `1.0` (just updated)
- **completeness**: Recalculate based on section coverage after the update
- **confidence**: Adjust based on the quality of evidence from the feature (higher if change-summary has strong traceability)
- **last_feature_sync**: Set to the current feature's `NNN-slug`

For knowledge docs NOT affected by this feature, deduct `0.05` from freshness (staleness decay).

#### 2e. Update glossary.yaml

Scan the feature's `spec.md` and `change-summary.md` for new domain terms:

- New entity names introduced
- New API endpoint concepts
- New business domain terminology
- New acronyms or abbreviations

Add new terms to `spec-kit/ai/knowledge/glossary.yaml` without removing existing terms. If a term already exists, update its definition only if the feature provides a more precise or updated meaning.

#### 2f. Create Integration Marker

Create `.knowledge-integrated` marker file in the feature directory:

```
spec-kit/specs/{NNN-slug}/.knowledge-integrated
```

Contents:
```
integrated_date: {YYYY-MM-DD}
knowledge_docs_updated:
  - {doc1.md}
  - {doc2.md}
glossary_terms_added: {count}
scores_updated: true
```

#### 2g. Append to CHANGELOG.md

Append an integration entry to `spec-kit/ai/knowledge/CHANGELOG.md`:

```markdown
## [{YYYY-MM-DD}] Feature Integration: {NNN-slug}

- **Feature:** {feature_name}
- **Knowledge docs updated:** {list of affected docs}
- **Sections modified:** {count}
- **New glossary terms:** {count}
- **Freshness scores refreshed:** {list of affected docs}
```

### 3. Clear Knowledge-Stale Markers

After processing all features, check `spec-kit/ai/knowledge/` for `.knowledge-stale.*` marker files:

- For each `.knowledge-stale.{doc-name}` file, check if the corresponding knowledge doc was updated during this run.
- If it was updated, **delete** the stale marker.
- If it was NOT updated (the stale marker references a feature not yet delivered), **keep** the stale marker.

## Operating Principles

### Knowledge Update Guidelines

- **Feature-ordered integration**: Always process features oldest-first to maintain chronological consistency in the knowledge base.
- **Targeted edits only**: Update only the sections affected by the feature. Do not rewrite entire knowledge documents during integration.
- **Steward sections are sacred**: Never modify `<!-- steward-authored -->` content. Only AI-synthesized sections are eligible for update.
- **Marker discipline**: Always create `.knowledge-integrated` markers after successful integration. This prevents duplicate processing.
- **Staleness management**: Clear stale markers promptly after updating the corresponding document. Stale markers drive urgency for `/speckit-update-knowledge` runs.
- **No invented knowledge**: All updates must trace to evidence in the feature's `spec.md`, `change-summary.md`, or the actual codebase. Never invent or assume facts (Constitution Principle 11).
- **Single Source of Truth**: Knowledge docs are the canonical source (Constitution Principle 5). Feature-specific details stay in `specs/NNN-slug/`; only generalizable knowledge propagates to `ai/knowledge/`.
